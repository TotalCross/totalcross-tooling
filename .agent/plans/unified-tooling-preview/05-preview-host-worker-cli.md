# Build the standalone preview host, worker, protocol, and CLI

This ExecPlan is Plan 05. It creates a process-isolated preview that can run
without Gradle, Maven, or VS Code.

## Purpose / Big Picture

A developer can run one Java command, open a desktop preview window, see a
TotalCross application frame, receive concise diagnostics, and close the preview
without terminating the build tool or leaking the application classloader.

## Current Architecture and Scope

Create these modules under `tooling-java`:

    tooling-protocol
    preview-worker
    preview-host
    tooling-cli

`tooling-protocol` contains no AWT, Gradle, Maven, VS Code, or TotalCross SDK
types. Use a versioned binary framing layer over a loopback TCP socket. The host
opens the server socket on `127.0.0.1`, generates a random session token, and
passes port plus token to the child process. The first worker message authenticates
the token and protocol version.

Use length-prefixed messages with explicit maximum sizes. JSON metadata is
acceptable for commands and diagnostics; frame payloads are raw copied ARGB or
PNG bytes with declared size and checksum. Reject oversized, malformed, or
unauthenticated messages before allocation.

## Plan of Work

Define small protocol messages for handshake, start, ready, frame, resize,
pointer, key, reload preparation, reload ready, diagnostic, stop, and closed.
Use one reader thread and a serialized writer per endpoint. Include request IDs
where a command needs an acknowledgment.

The worker receives SDK/runtime classpath, application classpath, main class,
arguments, display profile, and session connection details. It creates a fresh
application classloader, calls the Plan-04 runtime adapter through reflection,
copies frames into protocol payloads, forwards input, and closes the runtime
before process exit. It must never bind the host to TotalCross classes.

The AWT host displays frames, preserves aspect ratio, forwards normalized input,
and reports worker diagnostics. Keep window code separate from session/process
coordination so a later VS Code host can reuse the coordinator without AWT.

The CLI uses subcommands:

    totalcross-tooling preview --project <path>
    totalcross-tooling run --project <path>

For this plan, `--project` may accept an explicit session descriptor generated by
a test fixture. Build-tool discovery is added in Plan 06. Also support direct
arguments for application classes, SDK artifacts, main class, and display size.

Package an executable all-in-one CLI JAR without embedding SDK or application
classes. The CLI launches the worker with the tooling JDK selected by Plan 02.

Tests cover protocol version mismatch, invalid token, payload limit, child crash,
normal close, host close, frame transfer, input transfer, and application
classloader isolation. The end-to-end fixture renders a deterministic frame and
changes one pixel after a synthetic input event.

## Decision Log

- Decision: use a disposable child process as the production isolation boundary.
  Rationale: JVM class unloading and static SDK state are not reliable enough for
  repeated in-process reload.

- Decision: use loopback transport with a random token and explicit framing.
  Rationale: it supports Java, Gradle, Maven, and VS Code hosts without exposing
  an unauthenticated local service.

## Validation and Acceptance

Run module unit tests, then one end-to-end preview fixture. Acceptance requires a
visible window or headless host test that receives the expected frame, forwards
one input event, observes the changed frame, and closes with no worker left
running. Verify a worker crash produces a concise diagnostic and non-zero result.

Run the staged size checker and `git diff --check`. Do not begin build-tool
integration until the standalone path passes.

## Risks and Open Questions

Raw ARGB is simple but may consume bandwidth; PNG lowers bandwidth but adds CPU.
Start with one documented format and keep negotiated format extensible. Do not
optimize without measurement. macOS AWT startup may require the main thread;
record and test the chosen launcher behavior.

## Idempotence and Recovery

Session directories use unique IDs under the cache root and contain only
ephemeral metadata. On startup, remove only stale sessions whose process IDs are
not alive and whose age exceeds the configured threshold. A failed worker must
not corrupt installed SDK/JDK/tool state.

## Outcomes & Retrospective

Completed on 2026-07-26. The Java tooling now contains protocol, worker, host,
and CLI modules. Loopback sessions use a random token, protocol version, and
bounded length-prefixed messages. The worker emits copied ARGB frame payloads
and accepts lifecycle/input commands through a reflection-only SDK bridge. The
host keeps socket/process coordination separate from its AWT window, and the
CLI exposes `preview` and `run` entry points.

## Editorial Report

### Editorial Summary

The standalone boundary is functional and tested in-process with the same
socket/authentication path used by a child worker. The production worker entry
point and fat CLI JAR are packaged; build-tool project discovery remains in
Plan 06.

### Original Plan versus Actual Outcome

Added four Gradle modules, bounded binary framing, session authentication,
frame encoding, worker command dispatch, reflective runtime binding, AWT
window/input forwarding, and a fat-JAR CLI.

### What Changed

Raw copied ARGB was selected for the first protocol version. The neutral SDK
adapter is reached through reflection so the tooling modules do not link their
public API to SDK or AWT types.

### Decisions and Trade-offs

The first end-to-end test exposed response ordering and frame payload sizing
bugs; sending START acknowledgement before the initial frame and correcting
the fixed header size resolved both while keeping the protocol bounded.

### Unexpected Problems and Discoveries

`./tooling-java/gradlew -p tooling-java test --console=plain` passed all
available module tests, including the existing 8 tooling-core tests, protocol
round-trip/authentication tests, and host↔worker frame/input integration. The
fat JAR and install distribution built successfully; CLI `--help` and `run`
smoke commands passed.

`/tmp/tooling-plan05-package.log`. The executable artifact is
